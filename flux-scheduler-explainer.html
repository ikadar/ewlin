Section 1

The Big Picture

The Flux Scheduler takes all your print orders, machines, and operators as input, and produces a complete production schedule in milliseconds.

⚡
Key fact: The engine computes a complete schedule for 1,000+ tasks across 15 machines with operators in under 1 second. It can be re-run anytime with updated data — making it a planning assistant, not a one-shot decision.

What problem does this solve?

In a print shop with 15 machines, hundreds of active orders, and a team of operators with different skills and schedules, manually creating an optimal production schedule is practically impossible. The Flux Scheduler automates this by:

  • Respecting all constraints — machine availability, operator skills, task sequences, drying times, group capacity limits
  • Prioritizing deadlines — imperative orders get scheduled first; the system fights to meet every deadline
  • Optimizing operators — assigning the right person to each machine at each moment, accounting for skill levels, attention splitting, and autonomous machine operation
  • Self-correcting — the algorithm iterates multiple times, feeding real durations back to improve accuracy
  • Comparing strategies — it tries two different approaches and picks the better result
Section 2

Data Model — The Vocabulary

Everything the scheduler works with. Understanding these concepts is key to understanding the algorithm.

📑 The Job Hierarchy

Every print order follows this structure: Job → Elements → Tasks

🎯 Priority Tiers

Each job has a priority tier that determines how aggressively the scheduler fights to meet its deadline.

4×
Imperative
Contractual deadlines, financial penalties. The scheduler treats these as non-negotiable.
2×
Important
Key clients, strategic orders. Strong deadline pressure, but can yield to imperative.
1×
Standard
Normal production orders. The default priority level.
0.5×
Flexible
Internal orders, samples, tests. Can wait if capacity is needed elsewhere.

⚙️ Stations, Operators & Groups

⚙ Station (Machine)

A physical machine in the workshop. Each station has:

  • Operating schedule — when it's available (e.g., Mon-Fri 8h-17h)
  • Attention required — how much operator focus it needs (setup vs. run)
  • Masked-time capable — can it run autonomously after setup?
  • Group membership — capacity limits shared with similar machines
  • Max chunk duration — longest continuous run before forced break (default 7h)
  • Drying time — mandatory gap after printing (4h for offset presses)
  • Setup peremption — how long before an interrupted setup expires (default 2h)
  • Capacity — how many tasks can run simultaneously (default 1). Multi-capacity stations like Carton (table work) allow one independent task per available operator.

👷 Operator (Worker)

A human operator who runs machines. Each operator has:

  • Skills — which machines they can operate, with a proficiency level (0 to 1)
  • Weekly schedule — working hours per day
  • Absences — vacations, sick leave, appointments
  • Attention budget = 1.0 — total focus capacity to split across tasks
💡
Proficiency 1.0 = full speed. Proficiency 0.7 = 70% speed. The scheduler factors this in when choosing who to assign.

🔗 Station Group

A logical grouping of related machines (e.g., "All offset presses") with a maximum concurrent limit. For example, if the group allows max 2 concurrent tasks, only 2 presses in the group can run simultaneously — even if there are 4 presses in the group. This models shared resources like ink supply, ventilation, or operator availability.

Section 3

Constraints — The Rules

The scheduler must respect all of these rules when placing tasks. They represent physical reality — machines can't be in two places at once, ink needs time to dry, operators need skills.

⏳

1. Task Sequence

Tasks within an element must execute in strict order. You can't fold a cover before printing it.

✓ Print → Cut → Fold
✗ Fold → Print → Cut
🔗

2. Element Dependencies

Some elements depend on others. The binding element can't start until both the cover and interior elements are completely finished (last task of each).

✓ Cover done + Interior done → Binding starts
✗ Binding starts while Cover still printing
📚

3. Job Dependencies

Entire jobs can depend on other jobs. If Job B requires Job A, all tasks of Job A must finish before any task of Job B can begin.

✓ Insert Job complete → Catalogue Job starts
✗ Catalogue starts while Insert still in progress
☔

4. Drying Time

After printing on an offset press, ink needs 4 hours to dry before the next operation (cutting, folding, binding) can begin. This is a hard physical constraint.

✓ Print ends 10:00 → Cut starts 14:00 (+4h)
✗ Print ends 10:00 → Cut starts 11:00
⚙

5. Station Capacity

Each station has a capacity: how many tasks can run on it simultaneously. Most machines have capacity 1 (one task at a time). Multi-capacity stations like Carton (table work) can run several independent tasks in parallel — one per operator.

✓ Carton (capacity 3): 3 tasks with 3 operators
✗ Massicot (capacity 1): only 1 task at a time
📊

6. Group Capacity

Station groups enforce a maximum number of concurrent tasks across all machines in the group. This is separate from per-station capacity. If "All Presses" group has max 2, only 2 presses in the group can run simultaneously.

✓ Press A + Press B running (2 of max 2)
✗ Press A + B + C running (3 of max 2)
📅

7. Operating Hours

Tasks are only scheduled during a machine's operating hours. A task can span non-working time (overnight, weekend) but work only progresses during open hours.

✓ Scheduled within Mon-Fri 8h-17h
✗ Scheduled on Saturday when machine is off
🎓

8. Operator Skills

An operator can only be assigned to a machine they're trained on. Each skill has a proficiency level (0-1) that affects speed.

✓ Marc (skilled on Komori) → assigned to Komori
✗ Julie (no press skill) → assigned to Komori
📅

9. Operator Availability

Operators have their own schedules and declared absences (vacations, medical, etc.). The scheduler cannot assign an operator outside their working hours or during an absence.

⏱

10. Setup Peremption

If an operator is interrupted during the setup phase and doesn't return within 2 hours (configurable per machine), the setup expires and must restart from scratch. Ink dries, temperatures shift, paper humidity changes — the machine is no longer ready.

✓ Setup interrupted 30 min → resume OK
✗ Setup interrupted 3 hours → must redo setup
✅

11. Approval Gates

Before an element can be scheduled, all its prerequisites must be ready:

  • Paper — must be in stock or delivered (not still "to order" or "ordered")
  • BAT (Bon à Tirer) — proof must be approved by client
  • Plates — printing plates must be ready (not still "to make")
  • Formes — die-cutting forms must be delivered (not still "to order")

⚠ Currently warnings only — the scheduler will place tasks but flag the missing prerequisites.

Section 4

The Algorithm — Step by Step

How the engine turns chaos into a production schedule. Four phases, each building on the previous one.

0
Pre-Split (Chunking)
Prevent machine monopolization by splitting long tasks

Why split?

A task that runs for 14 hours would monopolize a machine for nearly two full working days. This blocks other urgent jobs from using that machine. The solution: split long tasks into chunks (max 7 hours each by default).

How it works

  • Any task longer than 7 hours (setup + run combined) is split into sequential chunks
  • Chunk 1 keeps the original setup time (the machine needs to be prepared once)
  • Chunks 2, 3, ... have zero setup time (the machine is already "calé" — configured for this job)
  • Chunks are linked by precedence: chunk 2 can't start before chunk 1 finishes
  • After scheduling, chunks are merged back into the original task for display

Why is setup not repeated between chunks?

Setup means preparing the machine for a specific job: loading the right paper, setting ink levels, aligning plates, calibrating. Once done, this configuration (calage) persists on the machine. If chunk 1 and chunk 2 run back-to-back on the same machine, the machine is still set up from chunk 1 — no need to redo it.

To make chunks stay together, the scoring formula includes a calage bonus (+100 points) for any task that continues the same job on the same machine. This strongly encourages the scheduler to place chunk 2 right after chunk 1, before switching to another job.

🔄 What if another job runs between two chunks?

If an urgent job (e.g., an imperative order with a score of 10,000+) outweighs the calage bonus, the scheduler may insert a different job between chunk 1 and chunk 2 of the same task.

When that happens, the other job changes the machine configuration (different paper, ink, plates). The engine detects this automatically: before starting chunk 2, it checks if the last action on the station was from a different job. If so, it restores the original setup time to chunk 2 by walking back through the predecessor chain to chunk 1 and copying its setup duration.

Ideal case: chunks stay together Chunk 1 (with setup) → Chunk 2 (no setup needed)
Machine stays configured. No time lost.
Interrupted: another job between chunks Chunk 1 → Urgent Job X → Chunk 2 (setup automatically restored)
Engine re-adds the setup. Schedule stays realistic.
⚡
How it works: At the start of every chunk 2+, the engine looks backward on the station timeline. If the previous occupant was a different job, the calage is broken — so it walks the predecessor chain to chunk 1, reads the original setup duration, and adds it back. The FBI loop then accounts for the longer actual duration in subsequent iterations.
1
Backward Pass — Computing LAST
Latest Allowable Start Time: when is the drop-dead date for each task?

Purpose

Before scheduling forward, the engine computes the absolute latest each task can start without causing its job to miss the deadline. This is called the LAST (Latest Allowable Start Time). Think of it as a countdown clock for each task.

How it works

The engine works backward from each deadline:

1

Start at the job's deadline

e.g., April 15 at 14:00 — this is the anchor point from which everything is computed backward.

2

Place the last task backward, tick by tick

Starting from the deadline, walk backward. At each tick, check: is the station free? Is the group below its concurrent limit?

3

Check operator availability at each tick 👁 detailed in Section 5

The backward pass uses the same operator selection engine as the forward pass. At each tick, it checks whether a qualified operator is available with sufficient attention — accounting for setup vs. run phase and masked-time mode. Ticks with no available operator are skipped, pushing the LAST earlier. This means operator scarcity directly tightens drop-dead dates.

4

Chain through predecessors

Move to the previous task in the element. Its deadline is now its successor's LAST. Walk backward through it the same way (station free + operator available). Repeat for every task in the chain.

5

Account for drying time

If a predecessor is a printing task, subtract an additional 4-hour drying gap before the successor's LAST.

6

Respect operating hours & group capacity

Skip non-working ticks (nights, weekends). If the station's group is at max concurrent capacity at a tick, skip it — the task can't run there.

7

Result: every task has a LAST

A hard date that says: "if this task hasn't started by here, the job will be late." The forward pass uses these to prioritize urgent work.

Ordering Strategy: Tier + Earliest Deadline

The backward pass combines two sorting criteria:

  1. Primary sort: by priority tier — imperative jobs first, then important, then standard, then flexible. This reserves machine capacity for high-priority jobs.
  2. Secondary sort: by deadline (EDD) — within each tier, jobs are processed earliest deadline first. The job due soonest reserves capacity before one due later.
💡
This means all imperative jobs are placed first (sorted by deadline among themselves), then all important jobs (sorted by deadline), and so on. The result: priority-based capacity reservation with deadline-awareness within each priority level.
2
Forward Pass — Building the Schedule
Actually placing tasks on the timeline, tick by tick

The Core Loop — Two Phases Per Tick

The engine advances through time in small increments called "ticks". Each station can define its own tick granularity (e.g., 5 min for a fast digital press, 30 min for a slow offset press — default 15 min). The engine computes the finest common granularity (GCD) and uses that as the global time step.

At each tick, the engine runs two phases: first it starts new tasks, then it processes all tasks that are already running. This means multiple tasks run concurrently and compete for operators at every tick.

Phase 1: Start new tasks

1

Identify eligible tasks

A task is eligible to start if: all predecessors are complete (including drying gaps), its machine has capacity, the machine group is below its concurrent limit, and it hasn't started yet.

2

Score and sort

Every eligible task gets an urgency score (detailed below). The most urgent task starts first. If it can find an operator for setup, it begins and joins the pool of active tasks.

3

Repeat at the same tick

After starting a task, re-score — another task may now be eligible on a different machine. Continue until no more tasks can start at this tick.

Phase 2: Process all active tasks 👁 operator details in Section 5

Every task that is currently running is processed at this tick. Active tasks are sorted by priority — more urgent tasks get first pick of operators.

1

Allocate operators globally

For each active task (highest priority first), find the best available operators from the shared pool. The full operator selection engine runs: skills, proficiency, attention budgets, continuity, masked-time fallback with switch threshold.

  • Full attention — operator gives 100% → full speed
  • Masked mode — operator monitors at reduced attention → per-station speed (e.g., 95%)
  • Waiting — no operator available → task stalls this tick
2

Compute productivity and advance work

Each task's remaining work decreases based on the attention it received. Tasks that finish are removed from the active pool, freeing their station and operator for the next tick.

💡
Why this matters: Because ALL active tasks compete for operators at every tick, the engine naturally handles:
  • Parallel masked execution — one operator splits attention across two masked machines simultaneously
  • Mid-execution handoffs — when a colleague becomes free, they take over a task automatically
  • Dynamic mode switching — a task can go from masked (95%) to full (100%) the instant an operator has nothing else to do

🎯 The Scoring Formula

How the engine decides which task is most urgent at any given moment:

// How much time is left before the drop-dead date?
slack = LAST - current_time - remaining_work

// Convert slack into urgency
if slack ≤ 0 → urgency = 10,000 + overdue amount // EMERGENCY!
if slack > 0 → urgency = (1 - slack/horizon) × 1,000 // proportional

// Apply priority multiplier
score = urgency × tier_weight // 4× imperative, 2× important, 1× standard, 0.5× flexible

// Bonus: is the entire job behind schedule?
if job_behind → score += overdue × 50 × tier_weight // massive boost

// Bonus: continuing the same job on this machine?
if same_job_on_machine → score += 100 // minimize changeover (calage)
💡
Key insight: A task with zero slack (at its drop-dead date) gets an emergency score of 10,000+, which always beats a task with positive slack (max 1,000). This means the scheduler will interrupt normal work to rescue a task about to miss its deadline.

Feedback-Based Iteration (FBI Loop)
Self-correcting through multiple passes

The Problem

The first forward pass uses estimated durations (setup + run time as declared). But in reality, some tasks may run in degraded mode (slower, because no operator was available). That means the actual duration is longer than estimated, which cascades — downstream tasks start late, potentially missing deadlines.

The Solution: Iterate

The FBI loop fixes this by feeding real durations back:

  1. Run backward pass → compute LAST values (drop-dead dates)
  2. Run forward pass → build actual schedule
  3. Check: did any tasks take longer than estimated? (degraded mode)
  4. If yes: feed actual durations back into backward pass
  5. Re-run backward + forward with corrected durations
  6. Repeat until stable (< 1% change) or max 3 iterations

4
Multi-Start — Try Two Strategies, Pick the Best
Because different orderings can produce different results
⚠
Multi-start is disabled by default (it doubles compute time). When disabled, only Tier+EDD runs. It can be enabled via the multi_start option in the compute request. It is also skipped if Tier+EDD already produced zero late jobs.

Why a second strategy?

The default strategy (Tier+EDD) reserves capacity for high-priority jobs first. But sometimes this over-constrains the schedule — a lower-priority job with a very tight deadline might get pushed too late because all capacity was reserved for higher-tier jobs that actually had plenty of slack. The pure-EDD alternative ignores tiers entirely and just goes by deadline, which can sometimes find a globally better solution. When enabled, the engine tries both and keeps the winner.

Key: Strategy B wins even though its makespan is longer (13d vs 12d), because it has fewer late jobs. Fewer late jobs always beats shorter total time. Meeting deadlines is more important than finishing fast.
Section 5

Operators — Attention & Masked Time

This is where 90%+ of scheduling complexity lives. The engine models operator focus as a numerical resource — split, shared, and re-evaluated at every tick.

🎯 5A. How the Engine Chooses Operators

The selection pipeline (runs at every tick, for every active task)

1

Filter candidates

From all operators, keep only those who: have a skill for this station (proficiency > 0), are available at this tick (within their schedule, not absent), and have remaining attention > 0 (not fully committed elsewhere).

2

Prefer continuity

Operators already assigned to this task from a previous tick are ranked first, regardless of score. This avoids handoff overhead and setup re-familiarization.

3

Filter by attention & score

Operators whose available attention is less than the station requires are discarded — regardless of proficiency. An operator with 0.3 free cannot work a station needing 1.0. Remaining candidates are scored:

score = remaining_attention × 50% + proficiency × 50%

This balances two goals: prefer operators with more attention to give (less fragmentation) AND operators who are better at this machine (faster work).

4

Allocate greedily, up to max_operators

Take operators in score order, allocating their attention until the station's need is met. Stop when: attention is satisfied, OR the station's max_operators cap is reached (physical limit on how many people can work the machine).

5

Handle insufficient attention

Non-masked machine: cannot operate with partial attention → task stalls (waits).
Masked-capable machine: falls back to masked mode if at least attention_masked is available (hard minimum, not "best effort"). If even that threshold isn't met → task stalls.

👥 5B. Max Operators Per Station

Each station has a physical limit on how many operators can work on it simultaneously (space, safety, ergonomics). The engine enforces this as a hard cap.

Station typeDefault max_operatorsRationale
Machine-paced (e.g., Massicot) 1 max_run_attention = attention_run → ceil(1.0/1.0) = 1. One operator, machine sets the speed.
Operator-paced (e.g., Hohner) 2-3 max_run_attention > attention_run → ceil(2.0/1.0) = 2. More operators = faster, up to the cap.
Masked mode (any masked station) 1 Autonomous operation — only one operator monitors. Always 1 during masked run, regardless of station max.

This is configurable per station. Even if 5 operators are free, a Massicot will only accept 1.

🔧 5B½. Multi-Capacity Stations (Table Work)

N operators → N independent tasks on the same station

This is different from multi-operator machines (where N operators work together on 1 task). On a multi-capacity station, each operator handles their own independent task at their own work position.

Multi-Operator Machine

e.g., Hohner (attention_run = 2.0)

2 operators → 1 task at 100% speed

💡
Key differences: On multi-capacity stations, there is no shared machine setup — so calage bonus does not apply (no setup alignment benefit) and chunk re-setup does not apply (no calage to break). Each work position is independent.

👁 5C. The Attention Model

Every operator has a total attention budget of 1.0 (100% of their focus). Each station declares how much attention it needs, per phase:

ParameterPhaseTypical valueDescription
attention_full Setup 1.0 Attention needed during setup. Can be < 1.0 for machines with simple setup. Per-station.
attention_run Run 1.0 Baseline attention for normal operation. The minimum for the machine to run at full speed.
max_run_attention Run = attention_run Max useful attention (operator-paced stations). Extra operators speed up to this ceiling.
attention_masked Masked run 0.5 Hard minimum for masked mode. If operator can't give at least this much, machine cannot run masked.
masked_productivity Masked run 0.95 Speed during masked mode. Per-station (e.g., SBG = 0.95, another press = 0.70). Not proportional to attention.

🤖 5D. Masked Time — Autonomous Machine Operation

Machines either run at full speed, run masked, or wait

A non-masked machine cannot operate with partial attention. Either the operator is fully present (100%), or the machine waits. Only masked-capable machines accept reduced attention.

🔄 5E. Dynamic Transitions — Tick-by-Tick Re-evaluation

Tasks can switch between masked and full mode mid-execution

The engine doesn't decide "this task runs masked" once and stick with it. It re-evaluates operator availability at every single tick. The logic at each tick:

  1. Try full attention with current operator — can the assigned operator give attention_run? If yes → full speed (100%). Continuity preserved.
  2. Evaluate the gain from switching — if the current operator can't give full attention, compute the productivity gain: 1.0 - masked_productivity.
    • Small gain (<10%) — e.g., masked at 95% vs full at 100%. Not worth switching operators. Keep current operator, go to masked mode.
    • Large gain (≥10%) — e.g., masked at 70% vs full at 100%. Try a different fully-available operator. If one exists and is qualified → switch to them at full speed. If not → fall to masked with current.
  3. Fall back to masked — keep current operator at attention_masked → masked mode (per-station productivity).
  4. Stall — if even masked threshold isn't met → task waits.
💡
Why a threshold? Switching operators has a real cost — handoff communication, re-familiarization. A 5% speed gain (95% → 100%) isn't worth the disruption. A 30% gain (70% → 100%) is. The 10% threshold balances continuity against idle operator waste.

Example: Marc operates SBG + MBO XL alone (both masked-capable)

Both machines need setup (1.0 attention each). Both are masked-capable (SBG: 0.95, MBO XL: 0.95). Marc is the only qualified operator for both. Setup requires full attention → he must do them one after the other.

What if Julie becomes available mid-execution?

Same scenario, but Julie (skilled on MBO XL) finishes another task at 11:00 and becomes idle.

👥 5F. Multi-Operator Machines

Some machines need or benefit from multiple operators. The engine handles two types, both capped by max_operators:

Machine-Paced

The machine sets the speed. Extra operators beyond the minimum provide no benefit. Example: a Massicot cutter.

max_run_attention = attention_run → max_operators = 1
Operator-Paced

More operators = faster. Productivity scales linearly up to max_run_attention, capped at max_operators people.

max_run_attention = 2.0 → max_operators = 2 → up to 200% speed

⏱ 5G. Setup Peremption

If an operator starts setting up a machine but gets pulled away, the setup can expire if the operator is gone too long.

Short interruption (<2h) Operator returns, resumes where they left off. No time lost.
Long interruption (>2h) Setup expired! Ink dried, temperature shifted. Must restart from scratch.

The threshold is configurable per machine (default: 120 minutes).

🔄 5H. FBI Feedback for Operator Issues

When tasks stall waiting for operators, or run slower in masked mode, the FBI loop catches it:

  • If a task's actual duration > planned duration (because it ran masked part of the time, or stalled waiting) → the feedback loop records the real duration
  • Next iteration: backward pass uses the longer duration to compute tighter LAST values
  • Forward pass then prioritizes the task earlier, reducing the chance of stalling again

This is how the scheduler self-corrects for operator scarcity: it learns from the first pass that certain tasks need to start earlier to account for operator bottlenecks.

📊 Additional Statistics

Tasks Placed

How many of the total tasks were successfully assigned to machines and time slots. Ideally 100%.

Deadline Violations

Individual tasks (not jobs) that end after their job's deadline. A single late task makes the whole job late.

Compute Time

How long the engine took to produce the schedule. Typically under 1 second for 1000+ tasks.

FBI Iterations

How many feedback loops were needed before converging. Usually 2-3 out of the max 3 allowed.

Degraded Tasks

Tasks that ran with insufficient operator attention. The schedule works, but these tasks took longer than ideal.

Warnings

Tasks that couldn't be placed at all (unresolvable conflicts), missing approval gates, or other anomalies.

🏆 Weighted Lateness Explained

Not all late jobs are equal. An imperative job 2 hours late is much worse than a flexible job 2 hours late. The weighted lateness formula accounts for this:

weighted_lateness = hours_late × tier_weight

// Examples:
Imperative job, 2h late: 2 × 4 = 8 weighted hours
Important job, 2h late: 2 × 2 = 4 weighted hours
Standard job, 2h late: 2 × 1 = 2 weighted hours
Flexible job, 2h late: 2 × 0.5 = 1 weighted hour
Section 7

The Complete Pipeline

End-to-end: from creating a job to seeing it on the Gantt chart. Here's how every piece connects.

1

User creates jobs in the web interface

Production planners enter print orders: reference, client, deadline, elements (cover, interior, binding), tasks for each element (print, cut, fold), setup/run times, station assignment, and priority tier.

2

Data stored in the database

Jobs, elements, tasks, stations, operators, and their relationships are stored in a PostgreSQL database via the PHP/Symfony backend API. This is the single source of truth.

3

User clicks "Calculer" (Compute)

On the scheduling page, the planner clicks the compute button. This triggers the automatic scheduling process. Any existing non-pinned, non-completed assignments are cleared to make way for the fresh schedule.

4

Backend assembles the compute request

The PHP API gathers all stations (with schedules, attention profiles, masked-time config), all operators (with skills, schedules, absences), all active jobs (with elements, tasks, dependencies), and station groups — then packages it into a single compute request.

5

Request sent to the Rust scheduling engine

The packaged data is sent as a POST request to the standalone Rust scheduling engine (a separate high-performance service). This is where the heavy computation happens.

6

Engine runs the full algorithm

The Rust engine executes the complete scheduling pipeline:

0 Pre-Split long tasks into chunks
1 Backward pass: compute LAST values (drop-dead dates)
2 Forward pass: place tasks tick by tick with operator assignment
3 FBI loop: iterate with real durations until convergence
4 Multi-start: try TierFirst + EDD, pick winner
5 Post-process: merge chunks, compute attention splits
7

Result returned to the backend

The engine returns the complete schedule: every task assignment (machine + time slot + operator(s)), quality scores (late jobs, lateness, makespan), and any warnings (unplaced tasks, degraded mode flags).

8

Assignments saved to database

The PHP API saves each task assignment to the Schedule entity (a versioned JSON document). The schedule version increments, ensuring consistency.

9

Frontend renders the Gantt chart

The web interface fetches the updated snapshot and renders two views:

  • Station Gantt — one column per machine, tasks as colored blocks
  • Operator Gantt — one column per operator, showing where each person works

Both views derive from the same data and are always synchronized.

Planner reviews and adjusts

The planner can manually adjust the schedule: drag tasks to different time slots, pin important assignments (protected from re-computation), mark tasks as complete, or re-run the engine with different parameters. The scheduler is a tool that assists human decision-making, not a replacement for it.

📝 Key Design Decisions

Greedy with global operator allocation

The algorithm is greedy — it makes the best local decision at each tick without backtracking. But it allocates operators globally across all concurrent tasks at every tick, not per-task in isolation. Higher-priority tasks get first pick. This enables parallel masked execution and mid-execution handoffs while remaining fast enough for real-time use. The FBI loop compensates for any remaining suboptimality.

Per-station tick granularity

Each station can define its own scheduling precision (default 15 min). A fast digital press might use 5-minute ticks for fine-grained scheduling, while a slow offset press might use 30-minute ticks. The engine computes the GCD (greatest common divisor) of all station ticks as the global time step, and snaps each task's duration to its station's own granularity.

Always real data

The engine works with real production data from the database — never mock or test data. This ensures the schedule reflects actual shop floor reality.

Compute replaces, not merges

Each computation replaces the existing schedule (except pinned and completed tasks). This avoids complex merge logic and gives a clean, globally-optimized result each time.
