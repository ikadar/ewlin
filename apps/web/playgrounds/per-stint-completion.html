Per-stint completion — modèle (task × operator × slot_start)

Playground exhaustif des impacts UX/UI/Algo de la décision : la complétion s'entend par stint (= une fenêtre op.from→op.to d'un opérateur sur une task), pas par task ni par chunk. L'agrégation aux niveaux supérieurs (chunk, task, job) est mécanique et garde le code Flux/KPIs inchangé.

API

API

Idempotent. Le client envoie le triplet (taskId, operatorId, slotStart) → le serveur upsert l'overlay. Le snapshot expose tableau aligné aux stints — le front lit par (operatorId, slotStart).

Règles d'agrégation

domain
stint.isDone = ∃ overlay(taskId, opId, slotStart) ∧ is_completed=true
chunk.aggregate = "all stints in chunk are done" → done · "some" → partial · "none" → pending
task.isCompleted = ∀ stint of task : stint.isDone
job.isCompleted = ∀ task of job : task.isCompleted

Impact algo — recompute préservant le done

Principe : seul le reliquat non-done est replacé

Engine

Quand le chef relance un compute après que des stints ont été marqués done, l'engine ne doit PAS replacer le travail déjà fait — c'est de l'historique. Concrètement :

  • Pour chaque stint done=true, le PHP construit un occupied_slot (stationId, [opId], slot_start, slot_end) et l'envoie dans ComputeRequest.occupied_slots.
  • L'engine pré-marque ces slots comme bloqués sur la grille avant le forward-pass (mécanisme qui existe déjà pour les pins safety-zone).
  • Si la task n'a plus que des stints non-done à placer, elle est partiellement re-schedulable — le forward-pass cherche une fenêtre pour le reliquat seulement.
  • Si TOUS les stints d'une task sont done → la task n'a plus rien à placer → exclue du payload.

Plomberie côté PHP — buildOccupiedSlots étendu

PHP

Aujourd'hui buildOccupiedSlots émet 1 slot par pin (user, in-progress, safety-zone). Demain il émet AUSSI 1 slot par stint done :

foreach (overlays where is_completed=true) { $slots[] = [ stationId: assignment.targetId, operatorIds: [overlay.operator_id], start: overlay.slot_start, end: matching_op_window.to, // depuis assignment.operators[] ]; }
Bénéfice subtil : un re-compute peut décider que le reliquat est mieux placé ailleurs sur la station, ou que d'autres opérateurs s'en chargeront. Mais le done historique est intouchable — on conserve la traçabilité opérateur réelle.

Cas limites algo

Engine
CasEffet
Stint done puis l'opérateur change d'avis (untoggle) L'overlay row passe à is_completed=false → plus dans occupied_slots → re-schedulable au prochain compute. Aucun jet de données.
Re-compute génère un nouveau découpage en stints (ex: l'opérateur n'est plus dispo) Les overlays done existantes restent — leurs slots sont préservés via occupied_slots. Les nouveaux stints non-done héritent de "pending".
Promotion préprod → prod avec stints done dans le payload Le payload prod fige le découpage. Les overlays s'attachent par (taskId, operatorId, slot_start) — un re-compute prod ne génère pas de nouveau payload, donc pas de drift.
Suppression de la task (jcf modifié) Cascade DB existante (FK CASCADE) supprime les overlays. Pas de fuite.

Synthèse

Maille reportée par l'opérateur : stint = (taskId, operatorId, slot_start).
Maille présentée au chef : agrégat task (Flux, JDP), agrégat chunk (grille station).
Maille engine recompute : stint preserved via occupied_slots ; reliquat seul re-placeable.

  • API : 1 nouvel endpoint stint-toggle (~30 lignes)

Total estimé : ~280 lignes effectives + tests. Modèle réaliste, pas de refactor du modèle de tasks, retro-compat préservée par operator_id=NULL/slot_start=NULL pour les overlays legacy.
