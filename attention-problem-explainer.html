Le Probleme d'Attention des Operateurs

Pourquoi l'algorithme ne peut pas (encore) imposer "attention complete obligatoire" sur les machines non-masked.

Le Scenario

Marc est le seul operateur qualifie sur SBG (presse, masked, 0.3 att.) et Polar 137 (massicot, NON masked, 1.0 att. obligatoire).

Le moteur doit scheduler les deux taches. Il les traite une par une, chacune du debut a la fin (modele sub-loop).

Le probleme fondamental : le modele sub-loop verrouille Marc pour TOUTE la duree de SBG. Quand Polar demarre ensuite, Marc n'a que 0.3 d'attention restante aux ticks ou SBG tourne encore. Polar a besoin de 1.0 — il ne peut pas fonctionner a 0.3.

Que faire quand Polar n'a que 0.3 d'attention ?

Trois choix possibles. Chacun a un defaut fatal.

Polar tourne a 30% de productivite avec 0.3 d'attention. La tache avance lentement.

Le probleme : Chaque tache qui attend bloque sa station. Les taches suivantes ne peuvent pas demarrer sur cette station. Avec 476 taches et des operateurs partages, les attentes se cascadent : A attend Marc, B attend la station de A, C attend B... Le temps de calcul explose. Le PHP timeout apres 2 minutes.

Pire : la sous-boucle de Polar avance tick par tick pendant l'attente. A chaque tick, elle cherche Marc (O(operateurs)), verifie l'attention, assigne la station... 200 ticks d'attente x 476 taches x 3 iterations FBI = le moteur tourne dans le vide pendant des minutes.

Le probleme : Le main loop verifie l'attention au tick de demarrage. Marc a 0.3 restant (SBG consomme 0.7). Le main loop rejette Polar. Il avance au tick suivant — Marc a toujours 0.3 (SBG tourne encore). Rejete. Et ainsi de suite jusqu'a la fin de SBG. Mais a ce moment, le main loop a deja depasse ces ticks.

Resultat : 392 taches sur 476 ne sont jamais placees. Le schedule est vide et inutile. Le calcul est rapide (65ms) mais ne sert a rien.
Impasse : Rapide + complet = faux. Correct + complet = timeout. Rapide + correct = presque vide. On ne peut pas avoir les trois avec le modele actuel.

Pourquoi le modele sub-loop cause ce probleme

Le verrouillage irrevocable

Quand le moteur schedule SBG, la sous-boucle tourne du tick 0 au tick 200. A chaque tick, elle inscrit l'attention de Marc dans la grille. Ces inscriptions sont permanentes — aucune tache ulterieure ne peut les modifier.

Quand Polar demarre ensuite, elle voit une grille deja gravee : Marc a 0.3 restant aux ticks 0-200. C'est un fait accompli. Polar ne peut pas "negocier" avec SBG pour recuperer de l'attention.

Modele Sub-Loop (actuel)

Chaque tache tourne du debut a la fin. L'operateur est inscrit dans la grille pour TOUS les ticks futurs d'un coup.

SBG demarre → Marc inscrit ticks 0-200 a 0.3
Polar demarre → Marc a 0.3 restant → BLOQUE

Les taches sont traitees une par une.
Pas de negociation possible.
VS

Modele Tick-by-Tick (objectif)

A chaque tick, TOUTES les taches actives se partagent les operateurs. Rien n'est verrouille a l'avance.

Tick 100: SBG veut Marc (0.3) → OK
Tick 100: Polar veut Marc (1.0) → 0.7 reste → ATTEND
Tick 201: SBG fini → Marc libre (1.0) → POLAR GO

Les taches sont traitees toutes ensemble.
L'attente est naturelle et bornee.

Pourquoi on n'utilise pas encore le tick-by-tick

Le probleme d'oscillation

On a essaye le tick-by-tick. Il causait un autre bug : a chaque tick, les priorites changent legerement. L'operateur rebondit entre les taches.

Tick 100
SBG ← Marc
Polar (attend)
Tick 101
SBG (attend)
Polar ← Marc
Tick 102
SBG ← Marc
Polar (attend)

Resultat : Marc apparait 4 fois sur la meme tache dans le planning. Le frontend affiche n'importe quoi. C'est le bug qu'on a vu en vrai.

La vraie solution (a implementer)

Le modele tick-by-tick + un mecanisme de verrouillage d'operateur :

  • Une fois assigne, un operateur reste sur sa tache sauf si explicitement libere
  • Le tri par priorite ne s'applique qu'aux slots non assignes
  • Un operateur peut etre libere quand : la tache finit, ou un collegue plus qualifie se libere (au-dela du seuil de 10%)

Ce mecanisme donne le meilleur des deux mondes : allocation globale (pas de verrouillage irrevocable) + stabilite (pas d'oscillation).

En resume : Le modele sub-loop ne peut pas imposer "attention complete". Le tick-by-tick le peut, mais il a besoin d'un systeme de verrouillage d'operateur qu'on n'a pas encore construit. C'est le prochain chantier.

En attendant : la solution cosmétique

Le moteur schedule en mode degrade (Option A). En post-traitement, il filtre les operateurs partiels (<0.5) sur les stations non-masked. Le frontend ne les voit pas. Ce n'est pas parfait — la duree des taches reflete la productivite reduite — mais c'est le meilleur compromis avec l'architecture actuelle.
